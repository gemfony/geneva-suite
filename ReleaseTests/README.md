# Geneva Release-Test Harness

A Python harness that builds Geneva and runs its test suite reproducibly across
a matrix of guest operating systems and compilers, inside containers, and
produces a pass/fail report. It drives the checks in `../ReleaseTestplan.md`.

Everything lives under `ReleaseTests/`. The harness does not modify any Geneva
source or build file.

---

## TL;DR

```bash
cd ReleaseTests

# 1. Diagnose the environment (backends + GPU) and get actionable advice:
python3 release_test.py doctor

# 2. Build the per-OS container images (Boost 1.91 from source, ~10-20 min each):
python3 release_test.py provision

# 3. Base mode: build Geneva (Debug, gcc + clang) and run ctest, both OSes:
python3 release_test.py run --quick --filter buildtype=Debug

# 4. Full release run (adds Release/Sanitize, benchmarks, MPI, long checks):
python3 release_test.py run --full
```

The harness needs only the Python standard library plus optional PyYAML (for
the config file). No other host dependencies beyond a container backend.

---

## Prerequisites

* **Podman** (default backend) — rootless, no daemon, no group membership
  needed. `sudo apt install -y podman`. Rootless requires subuid/subgid ranges
  for your user (usually configured automatically; `doctor` flags it if not).
* OR **Docker** — works too, but the invoking user must be in the `docker`
  group. Podman is preferred precisely because it avoids that.
* **Python 3.11+** and, optionally, **PyYAML** (`python3 -m pip install pyyaml`)
  to read `config.yaml`; without it the built-in defaults apply.
* Network access from the image build to `archives.boost.io` (Boost download)
  and the Ubuntu apt mirrors.
* For the **CUDA** matrix entries only: an NVIDIA GPU plus the container GPU
  toolkit (see "GPU / CUDA passthrough" below). Absent or mismatched GPUs are
  handled gracefully.

Run `python3 release_test.py doctor` first; it tells you exactly what is
missing and how to fix it.

## How the container / Boost approach works

* **One image per guest OS** (not per compiler). Each image installs BOTH a
  recent GCC and a recent Clang, plus CMake, Doxygen and (optionally) OpenMPI.
* **Boost 1.91.0 is built from source inside the image in C++23 mode**
  (`./b2 cxxflags="-std=c++23" ... install`) for the components Geneva needs:
  `atomic, json, program_options, regex`. It is
  installed to `/opt/boost` in the image.
* The **distro `libboost` packages are deliberately not used**: Ubuntu ships
  Boost 1.83 / 1.88 / 1.89, all older than the required **1.91**, and not
  guaranteed to be built in C++20 mode.
* **A single GCC-built Boost serves both the GCC and Clang Geneva builds.** On
  Linux, GCC and Clang share the same `libstdc++` C++ standard library, so a
  Boost compiled with GCC links cleanly against Geneva object code produced by
  Clang. This is confirmed by actually building Geneva with both compilers
  against the one image (see "Recorded results"). Only if a future Clang
  genuinely failed to link against the GCC-built Boost would a per-compiler
  Boost be warranted.
* The build **inside the container always uses `scripts/prepareBuild.sh`** with
  a generated `release.gcfg` (the same path real releases are built through),
  not a bare `cmake` call. `BOOSTROOT` in that `.gcfg` points at the in-image
  `/opt/boost`.
* The Geneva **source tree is bind-mounted read-only** at `/work/src`; a
  **writable per-job build dir** is mounted at `/work/build` from the work area
  (`/home/rberlich/Testplan` by default). The image stays read-only and
  reusable across jobs.

The Containerfile is generated by `releaseharness/backends/containerfile.py`;
`provision` writes it into `<workdir>/images/` and builds the image.

## The OS x compiler matrix

Base mode (`--quick`) builds the **base** feature set (tests + examples ON,
benchmarks/MPI/CUDA OFF):

| Guest OS    | Toolchain in image           | CMake  | Compilers built |
|-------------|------------------------------|--------|-----------------|
| Ubuntu 26.10| gcc 15.3, clang 22.1         | 4.3.4  | gcc + clang     |

Ubuntu 26.10 is the recommended platform (INSTALL), and its GCC 15 and Clang 22
are Geneva's compiler floor. Older Ubuntu releases are not in the matrix: 26.04
ships Clang 21 and 24.04 GCC 13.

`--quick` expands to OS x compiler x {Debug, Release}, i.e. **both Debug and
Release are built for every supported compiler on every guest OS** (8 base
cells: 2 OS x 2 compilers x 2 build types). `--full` additionally exercises
RelWithDebInfo and Sanitize build types, a minimal (all-options-off) build, and
a full-feature build (benchmarks + MPI, CUDA when a GPU is present), plus the
LONG-tier functional checks (consumers, all algorithms, networked example,
install / out-of-tree, etc.).

**Every build is a clean build.** `prepareBuild.sh --clean` is always invoked
(in both `--quick` and `--full`), so each matrix cell compiles from a pristine
directory — no artifact from a previous run can mask a problem. The per-cell
build directories are already namespaced by job slug
(`os-compiler-buildtype`), so different build types or compilers never share a
directory; `--clean` additionally guarantees a from-scratch compile on re-runs.
The difference between `--quick` and `--full` is therefore **only which checks
and (long-running) benchmarks run, never the cleanliness of the build** —
`--quick` skips the LONG-tier functional checks and benchmarks, not the
compile.

### Restricting to a single build type (for speed)

To run only one build type across the whole matrix, use `--build-type`:

```bash
python3 release_test.py run --quick --build-type Release   # 4 cells, Release only
python3 release_test.py run --quick --build-type Debug     # 4 cells, Debug only
```

This restricts the matrix *before* expansion, so the excluded build types — and
the hard-wired `minimal` (Debug) / `full` (Release) `--full` cells whose build
type is filtered out, and the excluded long-tier types — are never generated
(unlike `--filter buildtype=…`, which is a post-expansion narrow on the base
cells). The value is a comma-separated list of CMake build-type names
(`Debug`, `Release`, `RelWithDebInfo`, `MinSizeRel`, `Sanitize`); matching is
case-insensitive.

Geneva's requirements are GCC >= 15, Clang >= 22, CMake >= 3.27 and
Boost >= 1.91; the floor is enforced at configure time by
`CMakeModules/IdentifySystemParameters.cmake`. Every in-image toolchain meets
it.

## Commands

```bash
# Show the planned matrix; --dry-run also prints the exact container commands
# and the generated .gcfg without touching anything:
python3 release_test.py plan
python3 release_test.py plan --dry-run
python3 release_test.py --full plan --dry-run

# Build the per-OS images (on request only):
python3 release_test.py provision

# Base-mode build + ctest (SHORT tier), both Debug and Release on every cell:
python3 release_test.py run --quick

# Faster single-mode runs (only Release, or only Debug):
python3 release_test.py run --quick --build-type Release
python3 release_test.py run --quick --build-type Debug

# Narrow further with --filter:
python3 release_test.py run --quick --filter os=ubuntu-26.10,compiler=clang,buildtype=Debug

# Full release run (SHORT + LONG tiers; hours):
python3 release_test.py run --full

# Re-render the last saved report:
python3 release_test.py report
```

Useful flags: `--backend {podman,docker,multipass,auto}`, `--workdir PATH`,
`--config PATH`, `--build-type TYPE[,TYPE...]` (restrict to e.g. only `Release`
or only `Debug`), `--filter key=value[,...]` (keys: `os`, `compiler`,
`buildtype`, `label`), `--verbose`.

Configuration lives in `config.yaml`; every key has a built-in default, so the
file is optional.

## doctor — environment diagnostics

`doctor` classifies each backend and the GPU into an actionable state and
prints a recommendation:

* Backends: `ABSENT` (recommends the apt package) / `UNREACHABLE` (daemon down
  or rootless runtime broken) / `PERMISSION_DENIED` (Docker: not in the
  `docker` group) / `WORKING`.
* GPU: `ABSENT` / `UNREACHABLE` / `VERSION_MISMATCH` (NVML stale but CUDA
  compute may still work — recommends a reboot / kernel-module reload) /
  `WORKING`.

Example output on the reference host:

```
[ ok ] podman   : WORKING
        podman version 5.7.0
        -> Ready (rootless). This is the harness default backend.

[FAIL] docker   : PERMISSION_DENIED
        user not in the 'docker' group (daemon socket access denied)
        -> Grant access:  sudo usermod -aG docker $USER && newgrp docker  ...

[warn] gpu      : VERSION_MISMATCH
        NVML driver/library version mismatch (nvidia-smi fails, but CUDA
        compute may still work)
        -> Clear the stale kernel module: reboot, OR reload modules
           (sudo rmmod nvidia_uvm nvidia_drm nvidia_modeset nvidia;
            sudo modprobe nvidia). Ensure your user is in 'video'/'render'.
```

## GPU / CUDA passthrough

CUDA matrix entries run only on `--full` and only when a GPU is usable. A
driver/library version mismatch is treated as *usable-with-warning* (CUDA
compute still works), not absent.

* **Podman**: generate a CDI spec once on the host, then the harness passes the
  CDI device automatically:
  ```bash
  sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml
  # harness runs:  podman run --device nvidia.com/gpu=all ...
  ```
* **Docker**: install `nvidia-container-toolkit`; the harness passes
  `--gpus all`.
* If `nvidia-smi` shows a version mismatch, clear the stale NVML by rebooting,
  or reload the kernel modules:
  ```bash
  sudo rmmod nvidia_uvm nvidia_drm nvidia_modeset nvidia
  sudo modprobe nvidia
  ```
  Ensure your user is in the `video` and `render` groups for device access.

## Troubleshooting

* **`podman info` fails with a read-only `/run/user/<uid>` (libpod) error** —
  the rootless runtime directory is not writable. Ensure
  `$XDG_RUNTIME_DIR` (`/run/user/$UID`) is writable; enable a lingering user
  session with `loginctl enable-linger $USER`, or point `XDG_RUNTIME_DIR` at a
  writable path. (In a sandboxed shell this dir can be mounted read-only.)
* **Podman rootless: `subuid`/`subgid` not configured** —
  ```bash
  sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 $USER
  podman system migrate
  ```
* **Docker: permission denied on the socket** — add yourself to the group:
  ```bash
  sudo usermod -aG docker $USER && newgrp docker
  ```
  or just use Podman (the default), which needs no group.
* **Boost download fails during `provision`** — the image build pulls
  `boost_1_91_0.tar.bz2` from `archives.boost.io`; ensure outbound HTTPS works,
  then re-run `provision`.
* **GPU shows a driver/library version mismatch** — see "GPU / CUDA
  passthrough"; reboot or reload the kernel modules.
* **A build job fails** — per-check logs are written under
  `<workdir>/logs/<job-slug>.<check>.log`; the report (`<workdir>/reports/`)
  links each result to its log.
